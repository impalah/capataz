# Improvement roadmap

*Language: **English** · [Español](12-roadmap.es.md)*

Living list of pending improvements found during development, not committed to any milestone. Indicative priority: **high** (affects reliability or day-to-day operation), **medium** (known limitation, workaround available), **low** (technical debt or polish).

| # | Priority | Area | Description |
|---|-----------|------|-------------|
| 1 | High | Frontend — Executions/Audit | Pagination on the "Executions" and "Audit" tables is client-side only, over the first page already loaded: `AuditPage.vue` calls `api.audits()` without `page`, and `ExecutionsPage.vue` calls `executions.fetch()` without pagination filters. `q-table`'s page controls never trigger a new request to the backend, so beyond whatever fits in the first response, nothing else is visible even if it exists. Real `page`/`offset` need to be passed to the API when the user changes pages. |
| 2 | High | Catalog — UI | The "New service"/"Edit service" and "New action" forms in `CatalogPage.vue` only expose surface-level fields (id/name/group/environment/description for services; key/label/action_type/risk_level for actions). Everything that provides real functionality — a service's `container_selectors`, `health_config`, `grafana_config`, `loki_config`, `portainer_environment_id`/`stack_name`, and each action's `config` (playbook/inventory/extra_vars, or Portainer operation/target) — is only editable by importing YAML or calling the raw API. Any service/action created from the UI stays incomplete until it's finished some other way. |
| 3 | Medium | Catalog — import | `upsert_catalog` (used by the YAML import) never deletes services or actions that have disappeared from the YAML — it only upserts what's present. Decommissioning something requires an explicit `DELETE` via the API or a manual database edit; if the catalog flow gets documented or automated, this needs to be accounted for, or the real catalog and the YAML silently diverge. |
| 4 | ~~Medium~~ Resolved | API — live executions | ~~The `GET /executions/{id}/events/stream` SSE endpoint had become orphaned~~ — retired (2026-08, see `docs/code-review-2026-08.md` CR-020): the frontend was already using periodic polling in `ExecutionPage.vue` because `EventSource` can't send `Authorization: Bearer` and the stream never authenticated correctly outside `dev_mock`. If real-time push is wanted in the future, it will need a browser-compatible auth strategy (e.g. a short-lived stream token in the query string) before reintroducing the endpoint. |
| 5 | ~~Medium~~ Resolved | Frontend — tests | ~~No page has its own unit test~~ — resolved: `frontend/tests/unit/` has dedicated specs for all eight pages (`DashboardPage`, `ServiceDetailPage`, `ExecutionPage`, `ExecutionsPage`, `AuditPage`, `CatalogPage`, `LoginPage`, `AuthCallbackPage`), 131+ tests, 95%+ statement coverage. |
| 6 | Low | General observability | Two cases of silently swallowed exceptions with no log line were found and fixed (`StatusService` in the API, `tasks.py` in the runner) — the same pattern in two different places. Worth a review pass looking for other `except Exception:` (or other silent catches) that hide real failures without leaving a diagnosable trace. |
| 7 | Low | Frontend — Dashboard | Custom panels: allow creating panels with service groups freely chosen by the user (not necessarily matching `group_name`) and referencing them by their own URL (e.g. `/panels/:id`) so a subset of services can be shared or bookmarked. Requires a new persisted entity (panel + associated services, per-user or shared) and a new route/page in the frontend; nothing like this exists today — `DashboardPage.vue` always shows all services with group/environment filtering only in memory, no saved panels. |
| 8 | Low | Frontend — ServiceCard | Allow assigning a custom color to each service's card (`ServiceCard.vue`), to visually distinguish critical services or group them at a glance. Needs a new field on `Service` (e.g. `color`, hex) persisted and exposed in the YAML catalog, plus the corresponding styling in `app.scss`/`ServiceCard.vue`, taking care of contrast in both themes (light/dark). |
| 9 | Low | Backend + Frontend — Groups | Allow associating a color at the group level so that service cards in that group inherit it by default (with the per-service color from item 8 as an explicit override). Today `group_name` is just a loose `str` on `Service` (`domain/entities/models.py:29`) — there's no dedicated `Group` entity, which would need to be created (table + migration) before a color could be attached to it, and the inheritance priority service > group > default color would need to be defined. |
| 10 | Low | Packaging — Native apps | Evaluate Tauri to generate a desktop app (Windows/macOS/Linux) and a mobile app (iOS/Android) from the same Vue/Quasar frontend, instead of relying only on browser access to the SPA served by Nginx. This involves reviewing the current OIDC/PKCE flow (`frontend/src/api/oidc.ts`) for the redirect URI in a native-app context (custom scheme or loopback), and deciding how the binary is distributed and updated in a private homelab (there's no app store or auto-update channel today). |
| 11 | Medium | Architecture — Connectors (complex) | Today each `action_type` has exactly **one** global connection identity, fixed by environment/secret configuration, not per service: Portainer always uses the same `settings.portainer_url` + `portainer_token` (`api/src/capataz_api/core/settings.py:25`, read by `PortainerClient.__init__` in `runner/src/capataz_runner/executor.py:171-176`), and Ansible always uses the same SSH key / `known_hosts` / vault password from `runner/src/capataz_runner/config.py:81-100` for every host. This is already a real limitation with the current cluster (6 homelab nodes, one Portainer) and would be more of one if in the future we need to talk to several Portainer instances, or SSH into hosts with different credentials per service. Proposal: introduce a `Connector` entity (type + name + connection parameters) — e.g. a `portainer` connector with a `url` + reference to a token secret; an `ssh` connector with `host`/`user` + reference to an SSH key or username/password — so that `ActionDefinition`/`Service` reference a `connector_id` instead of assuming a single global configuration. It must keep the same secrets model as today (Docker secrets files referenced by name, never plaintext credentials in YAML/Postgres/logs — see `docs/06-security.md` and the "Secrets are Docker secrets files" rule in `CLAUDE.md`), add connector CRUD restricted to `capataz-admin` with its own audit trail, update `runner/src/capataz_runner/actions.py::resolve_action` and the `executor.py` adapters to resolve the connector before execution, and document the new field in `docs/05-yaml-catalog.md`. It also lays the groundwork for onboarding new `action_type`s (e.g. an `http`/webhook executor) without repeating the same single-global-credential problem. |

## How to use this list

When tackling an item, move it to an ADR (`docs/adr/`) or an issue if the project starts using them, and remove it from here. Add new items in the same format: what's broken or missing, exactly where (file/function if applicable), and what would be needed to fix it.
