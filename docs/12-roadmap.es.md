# Roadmap de mejoras

*Idioma: **Español** · [English](12-roadmap.en.md)*

Lista viva de mejoras pendientes detectadas durante el desarrollo, no comprometidas a ningún hito. Prioridad orientativa: **alta** (afecta a la fiabilidad o a la operación diaria), **media** (limitación conocida, workaround disponible), **baja** (deuda técnica o pulido).

| # | Prioridad | Área | Descripción |
|---|-----------|------|-------------|
| 1 | Alta | Frontend — Ejecuciones/Auditoría | La paginación de las tablas de "Ejecuciones" y "Auditoría" es solo del lado cliente sobre la primera página ya cargada: `AuditPage.vue` llama a `api.audits()` sin `page`, y `ExecutionsPage.vue` llama a `executions.fetch()` sin filtros de paginación. Los controles de página de `q-table` nunca disparan una nueva petición al backend, así que a partir de la página que quepa en la primera respuesta no se ve nada más aunque exista. Hay que pasar `page`/`offset` reales a la API cuando el usuario cambia de página. |
| 2 | Alta | Catálogo — UI | El formulario "Nuevo servicio"/"Editar servicio" y "Nueva acción" en `CatalogPage.vue` solo expone campos superficiales (id/name/group/environment/description para servicios; key/label/action_type/risk_level para acciones). Todo lo que da funcionalidad real — `container_selectors`, `health_config`, `grafana_config`, `loki_config`, `portainer_environment_id`/`stack_name` de un servicio, y el `config` de cada acción (playbook/inventory/extra_vars, u operación/target de Portainer) — solo es editable importando YAML o llamando a la API en crudo. Cualquier servicio/acción creado desde la UI queda incompleto hasta que se completa por otra vía. |
| 3 | Media | Catálogo — import | `upsert_catalog` (usado por el import de YAML) nunca borra servicios ni acciones que hayan desaparecido del YAML, solo hace upsert de lo que sí está presente. Dar de baja algo requiere `DELETE` explícito por API o edición manual en base de datos; si se documenta o automatiza el flujo de catálogo, hay que tenerlo en cuenta o el catálogo real y el YAML divergen silenciosamente. |
| 4 | ~~Media~~ Resuelto | API — ejecuciones en directo | ~~El endpoint SSE `GET /executions/{id}/events/stream` ha quedado huérfano~~ — retirado (2026-08, ver `docs/code-review-2026-08.md` CR-020): el frontend ya usaba sondeo periódico en `ExecutionPage.vue` porque `EventSource` no puede enviar `Authorization: Bearer` y el stream nunca se autenticaba fuera de `dev_mock`. Si en el futuro se quiere push en tiempo real, requerirá una estrategia de auth compatible con navegador (p. ej. un token de stream de vida corta en la query string) antes de reintroducir el endpoint. |
| 5 | ~~Media~~ Resuelto | Frontend — tests | ~~Ninguna página tiene test unitario propio~~ — resuelto: `frontend/tests/unit/` tiene specs dedicados para las ocho páginas (`DashboardPage`, `ServiceDetailPage`, `ExecutionPage`, `ExecutionsPage`, `AuditPage`, `CatalogPage`, `LoginPage`, `AuthCallbackPage`), 131+ tests, 95%+ de cobertura de sentencias. |
| 6 | Baja | Observabilidad general | Se han encontrado y corregido dos casos de excepción tragada en silencio sin dejar log (`StatusService` en la API, `tasks.py` en el runner) — mismo patrón en dos sitios distintos. Merece una pasada de revisión buscando otros `except Exception:` (u otros silenciosos) que oculten fallos reales sin dejar rastro diagnosticable.
| 7 | Baja | Frontend — Dashboard | Paneles personalizados: permitir crear paneles con grupos de servicios elegidos libremente por el usuario (no necesariamente coincidentes con `group_name`) y referenciarlos por una URL propia (p. ej. `/panels/:id`) para poder compartir o marcar como favorito un subconjunto de servicios. Requiere una entidad nueva persistida (panel + servicios asociados, por usuario o compartida) y una ruta/página nueva en el frontend; hoy no existe nada parecido — `DashboardPage.vue` siempre muestra todos los servicios con filtro de grupo/entorno solo en memoria, no paneles guardados. |
| 8 | Baja | Frontend — ServiceCard | Permitir asignar un color personalizado a la tarjeta de cada servicio (`ServiceCard.vue`), para diferenciar visualmente servicios críticos o agruparlos de un vistazo. Necesita un campo nuevo en `Service` (p. ej. `color`, hex) persistido y expuesto en el catálogo YAML, más el estilo correspondiente en `app.scss`/`ServiceCard.vue` cuidando el contraste en ambos temas (claro/oscuro). |
| 9 | Baja | Backend + Frontend — Grupos | Permitir asociar un color a nivel de grupo y que las tarjetas de los servicios de ese grupo lo hereden por defecto (con el color de servicio del punto 8 como override explícito). Hoy `group_name` es solo un `str` suelto en `Service` (`domain/entities/models.py:29`), no existe una entidad `Group` propia — haría falta crearla (tabla + migración) antes de poder colgarle un color, y definir la prioridad de herencia servicio > grupo > color por defecto. |
| 10 | Baja | Empaquetado — Apps nativas | Evaluar Tauri para generar una app de escritorio (Windows/macOS/Linux) y una app móvil (iOS/Android) a partir del mismo frontend Vue/Quasar, en vez de depender solo del acceso vía navegador a la SPA servida por Nginx. Implica revisar el flujo OIDC/PKCE actual (`frontend/src/api/oidc.ts`) para el redirect URI en contexto de app nativa (custom scheme o loopback), y decidir cómo se distribuye y actualiza el binario en un homelab privado (no hay tienda de apps ni canal de auto-update hoy). |
| 11 | Media | Arquitectura — Connectors (compleja) | Hoy cada `action_type` tiene exactamente **una** identidad de conexión global, fijada por configuración de entorno/secretos, no por servicio: Portainer usa siempre la misma `settings.portainer_url` + `portainer_token` (`api/src/capataz_api/core/settings.py:25`, leído por `PortainerClient.__init__` en `runner/src/capataz_runner/executor.py:171-176`), y Ansible usa siempre la misma clave SSH / `known_hosts` / vault password de `runner/src/capataz_runner/config.py:81-100` para todos los hosts. Esto ya es una limitación real con el clúster actual (6 nodos homelab, un solo Portainer) y lo sería más si en el futuro hay que hablar con varias instancias de Portainer, o con SSH a hosts con credenciales distintas por servicio. Propuesta: introducir una entidad `Connector` (tipo + nombre + parámetros de conexión) — p. ej. un connector `portainer` con `url` + referencia a un secreto token; un connector `ssh` con `host`/`user` + referencia a clave SSH o usuario/contraseña — de forma que las `ActionDefinition`/`Service` referencien un `connector_id` en vez de asumir la configuración global única. Debe mantener el mismo modelo de secretos que hoy (ficheros de Docker secrets referenciados por nombre, nunca credenciales en claro en YAML/Postgres/logs — ver `docs/06-security.md` y la regla de "Secrets son ficheros Docker secrets" en `CLAUDE.md`), añadir CRUD de connectors restringido a `capataz-admin` con su propio audit trail, actualizar `runner/src/capataz_runner/actions.py::resolve_action` y los adaptadores de `executor.py` para resolver el connector antes de ejecutar, y documentar el nuevo campo en `docs/05-yaml-catalog.md`. Sienta además la base para dar de alta nuevos `action_type` (p. ej. un ejecutor `http`/webhook) sin repetir el mismo problema de credencial-global-única. |

## Cómo usar esta lista

Al abordar un ítem, muévelo a un ADR (`docs/adr/`) o a un issue si el proyecto empieza a usarlos, y elimínalo de aquí. Añade ítems nuevos con el mismo formato: qué falla o falta, dónde exactamente (archivo/función si aplica), y qué se necesitaría para resolverlo.
